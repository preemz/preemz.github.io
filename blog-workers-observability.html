Observability on a Workers Free Plan (and What Paid Unlocked)

Primawan Satrio · August 2026 · ~8 min read

Our recruiting platform started on Cloudflare Workers' free plan. That bought us zero infrastructure and zero dollars, and it also bought us roughly zero dashboards: no APM agent, no log retention worth the name, no tracing. When a candidate's application vanished into a 1102 error one evening, my entire debugging surface was a Cloudflare error page and my own memory of what the code was supposed to do. The observability layer in this post was built under those constraints, and it is still running today, now on a paid plan.

This post is about the observability layer we built afterwards. It costs nothing, it lives in about forty lines of code, and for the failures it can see, it has surfaced them within minutes instead of when a recruiter phones me to ask if the site is down. The stack: tagged structured logs, a Discord Monitoring channel, privacy-sampled funnel metrics, and a cron smoke check that requests our own routes every fifteen minutes.

The constraint that shaped everything

On the free plan, console.log output was retained for a short window and there was no queryable long-term store to grep from a dashboard. So the design question was never "which observability vendor" but "where does signal go when logs evaporate?"

Our answer: logs stay for debugging what just happened, and anything that must be noticed gets pushed to a place the team already looks several times a day. For us that place is Discord. We already used a webhook for job announcements; we added a second channel, #monitoring, with its own webhook, and made it the single destination for every failure signal.

Figure 1. One metric() call always writes to Workers Logs. Only error-class events (names containing error, fail or _5xx) also post to the Discord channel. Dashboards are for browsing; Discord is for noticing.

One function to rule the telemetry

The core is a single exported metric(ctx, event, fields). It formats an event with key=value pairs and writes one tagged line to logs. If the event name contains error, fail or _5xx, it also posts to the Discord webhook; every other event stays in the logs. Every observable event in the codebase goes through it:

metric(ctx, 'cv_extract', { ext, ms, bytes, chars, ok: 1 });
metric(ctx, 'application_submit', { jobId, extras, portfolio, recruiter: 1 });
metric(ctx, 'worker_error', { path, method, err });

Three design rules keep it useful. Tag everything: every line starts with [metric] so a log dump can be filtered mechanically. Bound the fields: values are truncated to 60 characters so a stack trace fragment cannot flood a Discord message. Never log people: candidate emails, file contents, and names are excluded by rule; only technical dimensions (sizes, durations, counts, booleans, job IDs) pass through.

The privacy rule is enforced at the choke point. Because every event flows through one function, "what must never be logged" is checked in exactly one place, not sprinkled across the codebase as good intentions.

Funnel metrics: the business, measured

Error-only monitoring tells you the site is broken. It does not tell you the funnel is quietly leaking. We instrument the candidate journey as a sequence of metric events: CV extraction (with extraction success as an explicit boolean), application submission (with attachment counts), recommendation generation (with its own error event when the matcher fails). Reading a day of [metric] lines answers the questions that actually matter to a recruiting business:

  • Are CVs extracting cleanly, or is a document format silently producing garbage?
  • Do applications carry the extras (portfolio, additional files) we want?
  • Is the matching engine erroring on particular job orders?

The cv_extract event earns special mention because it is the direct descendant of the Error 1102 incident. After bounding PDF stream processing, we added ok (did extraction yield real text?) and timing to every extraction. When a pathological document appears now, the metric line shows it immediately: high ms, low chars, ok=0.

The smoke check: a cron that exercises our own routes

The piece that turned monitoring from reactive to proactive is a scheduled handler on a 15-minute cron. It requests a handful of our own pages (the home page, login, privacy, and the three newest job pages) and checks for 5xx responses. Failures land in the Monitoring channel with a red embed; successes write one quiet log line and notify nobody.

The quiet-success rule matters as much as the alerting. A monitoring channel that pings on every success gets muted within a week. Ours only speaks when something fails, so when it speaks, everyone reads.

The cron does not fetch our pages over HTTP. It hands each request straight to the Worker's own fetch handler, in the same process. We started with real HTTP, but a Worker that fetches its own hostname got a 522 back, and that produced false outage alerts. In-process still exercises routing, rendering and the D1 queries behind a live job page, and it caught a real regression once, a broken SQL path on job pages that would otherwise have sat undetected until an applicant hit it. Internal smoke coverage of live job pages came directly from that incident. What it cannot see is DNS, TLS or the edge. That is the job of a second check: after every deploy, CI runs a script that makes real HTTP requests to about two dozen anonymous GET routes plus one live job page. Neither check logs in or sends a POST, so authenticated pages and write paths are not covered.

What moving to a paid plan actually unlocked

The platform has since moved to a paid Workers plan. Here is the honest accounting of what changed and what did not, because upgrade posts usually oversell.

What genuinely improved: the upgrade was two subscriptions: Workers Paid and R2 Paid. Workers Logs retention went from three days to seven, queryable in the dashboard, which makes the weekly dry-run review of our GDPR retention sweep practical: I can read a week of retention_sweep dry_run=1 lines in one query instead of tailing at cron ticks. Debugging with a long delay (what happened at 3am six days ago?) became possible. From 1 December 2026, Cloudflare's docs list seven-day retention on the Free plan too, so that difference goes away. On R2, paid removes the anxiety of operating on free-tier object storage for a database of candidate CVs, the layer where the most sensitive documents live.

What did not change: everything in this post. The Discord Monitoring channel is still the thing that actually wakes me up; the tagged [metric] lines are still the format every event speaks; the smoke check still exercises our own routes on the same cron; the privacy rule that candidate emails never enter logs still holds at the same choke point. Paid tooling added memory to a system that already had reflexes. Build the reflexes first; they survive every plan tier.

What we would tell ourselves earlier

  • Observability is a routing problem, not a tooling problem. We did not need a vendor; we needed failure signals to arrive where the team already looks. Discord won because attention was already there.
  • One choke point beats scattered diligence. A single metric() function with a privacy rule and field bounding gives guarantees that twenty well-meaning console.log sites never will.
  • Instrument the funnel, not just the failures. A silent extraction degradation costs candidates quietly. Business metrics caught it; error logs never would have.
  • Free-tier limits forced honesty. Short log retention pushed push-based alerting from nice-to-have to mandatory. The constraint made the system simpler than a paid setup would have been, and when we later upgraded, the paid features became additions to a working system rather than a replacement for one (see the section below).
  • Alert only on failure, and only on what needs action. Every notification should be one a human must read. Everything else is a log line.

None of this is clever. A tagged logger, a webhook, a cron that calls its own routes. But the test of observability is not sophistication, it is whether the right person learns about a failure before a customer tells them. On that test this setup outperforms plenty of dashboards I have been bought and never opened.
