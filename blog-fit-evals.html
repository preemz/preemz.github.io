Measuring an AI Fit Assessment: 302 Frozen Decisions, 99 I Trust

Primawan Satrio · November 2026 · ~10 min read

Under the applications the team is working on KerjaBoard, my recruiting agency's job board, an AI model writes a short fit assessment: a verdict (Strong fit, Good fit, Possible fit or Not a fit), a few strengths and concerns, and for each one a quote from the CV or the posting that it rests on. The model is Claude Sonnet 5.5. I put it in production, the team uses it, and until this week nobody had measured whether it is any good. This post is about how I measured it, and what the measurement found, including the parts that do not flatter it.

The short version: on the cases where I trust the labels, the model agrees with the team 79.8% of the time (reading Possible fit as advance; 41.4% reading it as reject), and always guessing "advance" agrees 78.8% of the time. The interesting results are elsewhere.

The label is a recruiter's decision, and decisions are messy

There is no answer key for "is this candidate a fit". What exists is what the team did: it moved a card to Request to send profile (or further: Submitted, Interview, Offering, Hired), or it rejected the application. I turn that into a label, and most of the work was deciding which decisions deserve to be called labels:

  • Advanced means the card reached Request to send profile or later. That is an advance label.
  • Rejected after an advance gets no label at all. The client may have turned the candidate down after we sent the profile, and that says nothing about the model.
  • Rejected before any advance is a reject label, but only trusted if the move is in the activity log. That log started on 26 October. Earlier rejections might have been the client's call, so they are tagged status-unlogged, reported separately and never counted in the headline number.
  • A staff Disagree on the fit panel is a third source, feedback. These are the cases where a person overrode the model, so they are selected for the model being wrong. They are kept apart and never pooled into a model comparison.

A review pass before the first run found that my query counted the Today page's bulk close-out, which sweeps stale cards to Rejected, as a trusted rejection. Nobody screened those cards. The fix was one condition on the log row's kind and one test row; without the review that mistake would have sat inside the headline number.

Each decided application that has a CV file is frozen into a golden set together with its label and a copy of the job as it read that day, because an upstream sync rewrites job requirements and client briefs every day and a case must not change under the model. That gave 302 frozen cases on 64 orders: 91 advanced, 24 trusted rejections, 187 untrusted ones. Thirty-two had no readable CV (the CV text was missing or too short to assess), which leaves 270 that can be scored, and 99 of them carry a trusted label: 78 advances and 21 rejections.

A runner that cannot touch production

An eval run re-assesses the frozen cases with a chosen model. It writes to its own eval tables, plus one setting that feeds a footnote on the staff panel when the run is the production baseline, and nowhere else: not the stored assessments staff see, not the activity log, no email. A test drives the real route handlers with a data layer that records every write, and fails if a run writes anything outside that short list.

A Worker request has a time limit, so a run is advanced five cases at a time by pressing one route, and a small driver script presses it until nothing is left. A full Sonnet run of 302 cases took about eight minutes. The part that took thought was failure, because a measurement that quietly loses cases is worse than none:

  • Nothing to assess (no readable CV) is stored as that case's final result.
  • The request itself is wrong for every case (a bad key, a model name the API does not know) stops the step with the reason and stores nothing. This happened for real: Haiku rejects the thinking-effort parameter the production setup sends, the driver stopped on its first press and printed the API's message. Effort is now an option on the run.
  • An outage or a rate limit is not stored. The case stays pending, and the driver stops after three presses with no progress.
  • The model's own bad answer (malformed JSON, an empty answer) is retried and becomes final after three attempts, so a run always ends.

The review found one more: the production CV reader swallows every storage error and returns an empty string, which an eval would have stored as a permanent "No readable CV". A storage blip would have silently deleted cases from the measurement. Runs now read CVs with a strict reader that throws.

Agreement is meaningless without a baseline

Of the 99 cases with a trusted label, 78 were advances. A "model" that says advance every time agrees with the team on 78.8% of them. Sonnet agrees on 79.8% (95% interval 70.7 to 86.7), with Cohen's kappa 0.50 (interval 0.17 to 0.67). That is not distinguishable from guessing the majority class, and the report script now prints a warning whenever agreement is at or below that baseline.

There is a second trap in the verdict itself. Possible fit is neither an advance nor a reject, so every number is reported twice, once reading it as advance and once as reject. Read as reject, Sonnet agrees on only 41.4% (kappa 0.13), because the model rated 42 of the 78 candidates the team advanced as Possible fit. The honest figure is the pair, and any single number that hides which way Possible fit was read is a choice dressed as a result.

Figure 1. What the model said, by what the team did, on the 99 trusted cases. None of the 21 trusted rejections got Strong fit or Good fit, and 17 got Not a fit. But the team advanced 16 of the 33 cases the model called Not a fit.

That last sentence is the useful finding. In this sample the model never gave Strong fit or Good fit to a trusted rejection, but a Not a fit is not safe to act on alone: the team advanced about half of the cases it called that (16 of 33). Three caveats belong next to every number here. First, the team could see the assessment on the card when it decided (the feature went live on 22 October, and older or out-of-scope cards may never have had one), so agreement is flattered by an amount I cannot measure afterwards. Second, the 21 trusted rejections all come from the weeks since the log began, while the 78 advances come from all time. That mix inflates the 78.8% baseline and the one-in-two figure alike, and none of it is a clean sample. Third, 0 of 21 is consistent with a true rate of up to about 14%.

Intervals come from a bootstrap that resamples whole orders, not single applications, because the applications of one order are not independent: they share a job description and a recruiter's taste. Resampling cases one by one would give intervals that are too narrow.

A cheaper model, and why I am not switching

The product question was cost: can Claude Haiku 4.5 do this job? Same prompt, same 302 frozen cases, same code path. Haiku costs less than half as much per assessment. On the trusted cases its agreement is indistinguishable from Sonnet's when Possible fit is read as advance (a paired McNemar test gives p = 0.77), and clearly higher when it is read as reject (p below 0.0001), though as I explain below that second result is an artefact of how Haiku hands out verdicts. If agreement were the whole story, I would switch.

But "grounding" is the property that makes the assessment safe to show. Every strength and concern carries a quote from the CV or the posting, and the server checks each quote against the source and drops the ones it cannot find, so a reader never sees a quote that is not in the source. Sonnet had 3.4% of its quotes dropped. Haiku had 28%. It also produced ten keyword hits for protected words (age, nationality, religion and the like) in its prose, spread over six assessments, against one hit in one Sonnet assessment (a keyword match over-counts, for example on "race condition", so these are hits to read, not confirmed leaks), it ran slower with the thinking setting off, and it handed out Strong fit almost three times as often. The apparent edge for Haiku when Possible fit is read as reject comes from exactly that generosity: it turned Sonnet's Possible fits into Good fits. I am staying on Sonnet, for grounding and leakage, not for agreement.

To check how much the model disagrees with itself, I re-ran Sonnet on a 40-case sample. Three had no CV; of the other 37, one verdict changed (2.7%). That is a small sample: the 95% interval for the true rate runs from under 1% to about 14%.

What turned up that had nothing to do with the score

While building a second feature that reads the same scrubbed CV text, I read exactly what the model is sent, and that turned up a privacy bug. Before the model reads a CV, KerjaBoard strips the name, contact details and the lines that state nationality, age and similar. A CV extracted from a PDF with one word per line carried a phone number split across lines, and the scrub that looks for phone numbers works line by line, so the number survived into the prompt. The fix joins the lines first and scrubs second, with a test that failed before the change. That bug had been live, and it surfaced because I was reading the pipeline for another reason, not because anything flagged it.

Three things carry on after the experiment. Staff get Agree and Disagree buttons under each assessment, so the golden set keeps growing from real corrections (an Agree is not a label, because the person already read the verdict). A daily check compares the share of dropped quotes in the last week with the 23 days before, and also flags an error rate above 10%; it posts to a monitoring channel only when one of those two thresholds is crossed. And the privacy notice now says that past applications are sometimes re-run through the model to check accuracy, with no CV text kept.

What this does not show

  • It says nothing about candidates the team never decided. The labels exist only where a person acted.
  • Rejections are not all about fit. A salary mismatch or a closed order is a reject label too, so agreement cannot reach 100% even for a perfect model.
  • I did not test whether the client brief moves the verdict, or any second prompt. The runner has a switch for hiding the brief, which I have not used; a second prompt needs a code change, and the prompt version is recorded so runs on different prompts are never compared as one.
  • 99 trusted cases is small. The agreement interval is 16 points wide, and every comparison here that looks like a difference should be read against that.

The assessment rarely rates a trusted rejection highly, but a Not a fit is wrong about as often as it is right, and more than half of the candidates the team advanced were rated only Possible fit. I know that now with an interval attached, which is more than I could say last week.
