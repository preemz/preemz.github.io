Designing a CV Reformatter: Any Resume In, the Client’s Exact Template Out

Primawan Satrio · October 2026 · ~12 min read

Every client of my recruiting agency wants candidate CVs in its own Word template. One wants a blind CV with the candidate's name in the header and the client's own contact block in place of the candidate's. Another wants the full profile, with a line for how long the candidate has worked in Singapore. When a client has no template, we send our own anonymous Satrio Consulting CV, so the client hires through us rather than around us. Before this tool, a recruiter retyped each CV into the right template by hand, for every candidate and every client.

The CV reformatter inside KerjaBoard, our job board, does that work now. A recruiter picks a candidate from the database or uploads a file, picks the client format, checks the draft on a review screen, and downloads a finished .docx in the client's template. It went live in August 2026, the internal recruiting team uses it on real client submissions, and their verdict so far is that it works. This post is the system design: the stages, the decision behind each one, and the bugs that shaped them.

The shape of the pipeline

Eight stages across two requests. Everything runs on the same Cloudflare Worker as the rest of KerjaBoard, and the document path (PDF parsing, the model call, the Word renderer) uses no npm packages.

Figure 1. The reformatter pipeline. The first request ends at the review screen; the download is a second request, built only from what the recruiter approved.

The split into two requests is the most important decision in the design. The model's output is a draft, never a document. Nothing reaches a client until a recruiter has read every field, and the download is rebuilt from the fields the recruiter submitted, so a correction made on the review screen is the version that ships.

One definition, three consumers

Each format is one object in CLIENT_FORMATS: groups of fields, a repeating block for work history, and flags such as blind, anonymous and english. That one object generates the JSON schema in the prompt, the inputs on the review screen, and fixes the key names the template's tokens must use.

Figure 2. A format definition drives the prompt, the review form and the template. A field added to the definition reaches the prompt and the review form automatically; the template only has to use the same key.

The alternative, a prompt, a form and a template each written by hand, drifts the first time someone renames a field: the model fills a key the template never reads, and the client gets a blank section. With one definition, a new format is a short list: the object, the template file, one entry in a lookup table, and a line in the in-app guide. Prompt rules check the flags rather than the format's name where they can, so the newest format reused a translation rule an earlier format needed.

Extraction is the hard part

The first serious bug report said the reformatter was "not accurate". Every field on the review screen read xxxx. That is not an accuracy problem; it is zero input. The PDF parser had returned an empty string, the model had been asked to read nothing, and it had correctly answered that nothing was there. Tuning the prompt would have changed nothing.

PDF is not a text format. It is a set of drawing instructions, and the tools people use to make CVs store the letters in at least five different ways. The parser in src/cv.js learned each one from a real CV that came back empty or garbled:

How the text is storedWhat we sawThe fix
Compressed streams with stray bytes before endstreamEvery field emptyInflate exactly the stream's declared /Length, not up to the end marker
Glyph IDs in hex, a constant offset from Unicode (common in DOCX-to-PDF converters)No text at allRead the offset from the file's own ToUnicode maps and take the most common one
One ToUnicode map per font subset, the same code meaning different lettersReal words mixed with wrong charactersDecode each string through the map of the font in use at that point
Glyph indices with no ToUnicode map at allText shifted into nonsenseSearch offsets per font; score each on letters, vowel ratio and common letter pairs
Uncompressed or ASCII85-wrapped streamsAn empty string from a plain English CVRead raw streams as they are; decode ASCII85 before inflating

Row four was the subtle one. Scoring candidate offsets by letter count alone picks a neighbour three or four places away, which turns a heading into readable-looking nonsense. Adding vowel ratio and a small set of common English and Indonesian letter pairs is what broke those ties. That change was run against a corpus of about three thousand real CV files, old parser against new: it improved 265 and made none worse. Later extractor changes were checked the same way on smaller sets, and the newest class has its own test in CI.

Two guards sit around the extractor. A looksReadable check refuses mojibake before the model call, with a message asking the recruiter to re-save the file as DOCX, because sending garbage to a model three times with retries just produces three empty answers. And each text operator is found with a linear scan before any pattern matching runs: one image-heavy Japanese CV form made the old regular expression quadratic, and the Worker ran out of CPU time.

The model call

The prompt is mostly rules about facts. Copy every degree, GPA, certificate, employer and date exactly as written. Include every employer. Never guess: an unknown field is the literal string xxxx and an unknown list is empty. For clients who want English, translate the prose but keep proper nouns as written, so a product or system name is not turned into something the client cannot search for.

The call goes to Claude Sonnet with low thinking effort, because thinking spends the same output budget the JSON needs. The answer is parsed leniently: markdown fences are stripped, and JSON cut off mid-object is closed at the last complete element, so a long CV still reaches review with most of its data instead of failing on "Unexpected end of JSON input". A truncated answer is reported as running out of output space and is not retried, because a retry would stop in the same place. Empty answers and server errors get up to three attempts, with a longer wait before each retry.

Why not a free model? I measured it in August 2026 with the production prompt. On a clean CV, Claude and two free Workers AI models scored the same. On the same CV with its line breaks stripped and a section cut out, both free models returned nothing usable, while Claude still extracted five of six jobs and the correct GPA. A later re-run on newer cheap models did much better, so that verdict belongs to that generation of models, not to free models in general. The code now has a triage step that can send clean CVs to a cheaper model; it is built and switched off until an A/B run says it is safe.

Four errors, four causes

Over two months the provider call failed in four different ways, and each one looked like a broken formatter to the recruiter who hit it:

  • 401: billing on the API account, not the key itself. A new key fixed it without a deploy.
  • 404 naming the model: the model ID had been retired. It lived in two places, the config and a fallback in the code, and both had to change.
  • 400 asking for a workspace header: the provider tightened authentication for service-account keys. The key was fine; the request needed one more header.
  • 403 "Request not allowed": a Worker's outbound call leaves from the data center nearest the visitor, and the provider refuses some regions. The fix is a Durable Object created once with a Western Europe location hint. Durable Objects stay where they were first created, so every model call now leaves from the same region, whoever clicks the button.

The lesson: read the status code and the body before touching anything. I also added an admin-only page that makes a real call with the configured model. Its first version left out the workspace header and reported a working key as broken. A health check has to send exactly what production sends, or it is worse than no check.

A review screen that shows the gaps

Every field on the review screen is editable, every field the model could not fill is highlighted in yellow, an empty single-value field reads xxxx, and a list of the gaps sits at the top of the page. I chose visible gaps over a cleaner-looking draft on purpose. A draft that has to look complete invites a guessed notice period; a draft that shows xxxx asks a person to find out. The xxxx marker also survives into the Word file if nobody fixes it, so a missing value cannot pass for an answer. Empty lists are the exception: their section is dropped from the document, so the yellow highlight is what catches those.

Filling Word templates with no dependencies

A .docx file is a ZIP archive of XML. The renderer in src/docx.js reads the client's template, rewrites only word/document.xml, and copies every other part byte for byte, so the client's logo, fonts, styles, headers and numbering stay exactly as they made them. The ZIP reader and writer, the CRC32 and the token engine are about four hundred lines of plain JavaScript inside the Worker.

The template grammar is small: {{name}} for a value, a paragraph that repeats once per list item, and a block loop for work history. The traps were all in Word's file format:

  • Word splits text across runs. A token typed in one go can be stored as three fragments with different formatting. Loop markers and old text in a template are matched on the paragraph's combined text; simple {{tokens}} are still matched one run at a time, which is why every template is written with each token in a single run.
  • ZIP sizes can live only at the end. Many Word files write zero sizes in the local headers and the real ones in the central directory. Reading local headers returned zero characters; the reader now starts from the central directory.
  • Templates carry old data. One client template had a previous candidate's name drawn into the banner at the top of its first page. The renderer replaces that text across runs with the current candidate's name, and the template's placeholder portrait is swapped for the uploaded photo in the same frame.
  • Empty sections should disappear. A heading with nothing under it is dropped, so a candidate with no trainings does not get an empty Trainings section.

Anonymous CVs: three layers, because one is not enough

Our own anonymous CV carries no name, email, phone, address or link, because the client should contact us, not the candidate. A prompt rule saying so is not enough: models copy sentences verbatim, and "contact me at" comes along with them. So identity is removed three times:

  • The prompt forbids the name and every contact detail, and asks for "the candidate" instead.
  • A scrub on the draft removes emails, links, social handles, phone numbers and the candidate's name, using the database name when the candidate was picked, or a checked guess from the CV's header on an upload. A sentence that existed only to give a contact detail is dropped whole.
  • A second scrub on download, by pattern only, because the review screen is editable and a recruiter can paste a phone number back in.

The scrub had its own false positives to get right. A rupiah figure such as 3.000.000.000 looks like a phone number until you require a phone prefix and reject thousands groupings. A name can also be part of a company name: Jaya is both a given name and a common word in Indonesian company names, so a name part that appears in an employer or school line is kept. And JavaScript's \b fails on names with accents or Chinese and Japanese characters, so word boundaries use Unicode letter classes. Twelve cases like these, plus a rendered document checked for leftover identity details, run as a test in CI before every deploy.

One gap I know about: the download request does not know the candidate's name, so the second scrub catches contact patterns but not a name the recruiter types back in on the review screen. The review page says how many details were removed, and the recruiter is the last check. Closing it properly means carrying the identity through the form, which I have not built yet.

The bug at the last click

The reformatter started as admin-only. When the internal team needed it, the obvious move was to reuse the admin routes, but the /admin paths sit behind an extra login at the edge that only admin passes, so staff were blocked before the app's own permission check ever ran. The team got parallel /internal routes. Two bugs followed. The first attempt renamed the admin upload route instead of adding a new one, which broke it for admin. Later, the review form posted to an /internal download route that did not exist, so the team could upload and review a CV and then hit "Page not found" on the final click.

After any route change I now send a request to every route in both namespaces and expect a login redirect, never a 404. The automated smoke test after each deploy covers only the admin page so far. The rule I took from it: when a second role needs a feature, add routes, never rename the existing ones.

What is not solved

  • Scanned CVs. An image-only PDF has no text layer, and there is no OCR path yet. The recruiter is asked for a text-based file.
  • Cost routing. The triage step that would send clean CVs to a cheaper model stays off until an A/B run on real CVs shows that the cheap path does not miss or invent fields.
  • The name on the download request, as described above.

None of the parts is exotic: a PDF parser, one LLM call behind a schema, a review form and a ZIP writer. The design work was in the seams: one definition behind the prompt, the form and the template; the model's output treated as a draft that a person approves; and every gap made visible instead of plausible.
