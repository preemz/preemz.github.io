Building a Client CRM on Cloudflare Workers, One Weekend

Primawan Satrio · October 2026 · ~10 min read

For two years my agency kept its client pipeline in a Google Sheet. Companies in one tab, event contacts in another, reach-outs and replies typed by hand into cells that never lined up. That sheet was the system of record for every business development conversation we had. Satrio CRM is what replaced it, and this post is how it was built.

What it is, plainly: an internal tool for the business development team. It is not a SaaS product, there is no marketing site, and nothing here is for sale. More than 500 companies and contacts came out of those sheets and into a real database, on one Cloudflare Worker with one D1 database, server-rendered HTML and zero runtime dependencies.

Why a CRM, and why build it

The honest answer for the build decision: the sheet already held everything, and every paid CRM wanted the same data entered again, by hand, in its own shape. The sheet had no way to answer the questions we kept asking. Who did we reach out to last month and who replied? Which of our five market segments is producing qualified meetings? Who has asked us to stop emailing them, and did anyone actually stop?

Those questions are three SQL queries. So the tool that answers them is a database and some pages over it, which is the smallest thing that could possibly work: one Cloudflare Worker, one D1 database, no framework and no build step. The app is vanilla HTML, CSS and JavaScript rendered on the server. The only npm dependency in the whole project is a parser for incoming email, and it lives in a separate Worker.

I have shipped three systems like this now, so the pattern is proven rather than novel. The reason to write it down is not the CRUD. It is the outbound engine that came after it, and the two bugs I found by testing that engine against real sentences instead of against itself.

The sheets were not clean data

A CSV export of two years of business development looks like data until you try to load it. The importer I wrote is deliberately tolerant: every messy cell gets logged, and nothing is ever silently dropped.

  • Idempotent by design. Re-running the import is safe, because rows are keyed and re-imported rather than appended. An import you can run twice without corrupting anything is worth more than a fast one you cannot.
  • Messy cells are parsed, not skipped. Some contact cells held a name, a job title, a company and an email address in one field. Those are pulled apart into the right columns rather than dropped for being the wrong shape.
  • Duplicate company names get a second chance. Company names are not unique, so a reused company id falls back to a name match instead of becoming a second row for the same company.
  • Written in chunks, and every chunk reports back. Each chunk is applied separately and its result is verified, so a partial apply is visible instead of quiet. D1 has a statement limit, and a script that stops halfway should say so loudly.
  • Dry run first. The default run changes nothing. It prints what it would do, so the real run is never the first time you see the decisions it made.

Zero dependencies still needs real auth

No auth library means writing the security parts yourself, which is only a good idea when you do it carefully. Passwords are PBKDF2-SHA256, 100,000 iterations, and compared in constant time. Sessions are rows in the database with a seven-day expiry, in an HttpOnly cookie, checked on every request and deleted on sight once expired.

Every form carries a double-submit CSRF token: a random value in a cookie, echoed in a hidden field, compared byte for byte. The server-side html() helper stamps every POST form automatically, so a new form cannot be added without it. This is the part I would not hand-roll casually, and the reason it is acceptable here is that the same scheme has run in two other production systems of mine.

The part that was actually interesting: outbound

A CRM that only stores what you typed in is a database with extra steps. The reason this one is worth writing about is that it also runs outbound: segments the companies, tracks outreach, reads the replies that come back, and sequences follow-ups.

Replies are read by a second Worker, wired to Cloudflare Email Routing, that shares the first Worker's database. When a reply arrives it does four things, in this order:

  • Classify the reply. A pure function takes the subject and body and returns one of interested, question, out of office, unsubscribe, or bounce.
  • Log it to the company. The reply becomes an entry on that company's timeline, so the conversation is in the same place as everything else.
  • Honour an opt-out immediately. An unsubscribe or a bounce adds the address to the suppression list, and a suppressed contact is removed from any sequence they are in.
  • Alert the team. A Discord message for every reply, so an interested prospect does not sit unread. Alerting is best effort and never allowed to break the processing.
Figure 1. What happens when a reply arrives. Suppression is checked by every send path, not only here.

Suppression is the one rule with no exceptions in the codebase. It exists because of Indonesian law (UU 27/2022) and, for European contacts, GDPR. A single hot lead is never worth mailing someone who asked you to stop.

Sending slowly on purpose

A new mailbox that sends 200 cold emails on its first day gets flagged, and the flag outlives the campaign. So the sequence engine enforces a warm-up ramp: a mailbox starts at 5 sends a day and climbs 5, 8, 12, 18, 25, 35, 50, then stays there. The cap is per mailbox per day, and the ramp is a decision made once, in a pure function, rather than a setting somebody can get wrong under pressure.

Figure 2. The warm-up ramp. Day 0 is the mailbox's first send, not the sequence's first send.

Enrolment is idempotent, each contact gets a stable A/B variant derived from its id so a contact sees the same variant at every step, and the whole scheduler is pure: given an enrolment, the suppression set, the clock and today's send count, it returns whether to send and why. Every reason it might not send is a named verdict, which is what makes the caps testable without any email infrastructure.

The tests passed, and the classifier was wrong

The reply classifier is a set of regular expressions, and it had nine tests. All nine passed. Then I fed it sentences a real prospect would actually write, and it got three of them wrong:

  • "We have 550 employees in Jakarta, can you send pricing?" read as a bounce, because 550 matched a bare SMTP error code. This is a qualified prospect asking to buy, and a bounce adds the address to the suppression list. One regex could have permanently silenced them.
  • "Thanks, but we're not interested at the moment." read as a hot lead, because the word "interested" was there and nothing checked whether anyone had negated it. The system would have paged the team about a no.
  • "Please don't unsubscribe me, I'd like to learn more." read as an opt-out, because it contains the word "unsubscribe". A warm reader would have been suppressed for politely telling us to keep going.

The tests passed because every test case was a sentence written to match the regexes. That is the real lesson, and it is the same one from the scoring engine post: a test that has never failed has not proven anything. Testing a classifier against its own author's examples tests the author's imagination, not the code.

The fixes: a bounce now has to say why delivery failed, because a number in a sentence is not an SMTP code. Interest only counts when nobody negated it. An opt-out does not count when the writer explicitly asked us not to opt them out. And there are now eight regression tests, each one a real sentence, and each one one that the previous version got wrong. A reply that both declines and asks to be removed is still an opt-out, because a missed opt-out is the one error that costs real trust.

The other bug: a kill switch anyone could arm

The send path had a safety switch so that no cold email could leave before the domain's SPF, DKIM and DMARC records were set up and the mailbox was warmed. The switch was read from a form field in the request. Any signed-in user could arm it by posting send_enabled=1. A safety gate that the person it is protecting against can turn on is not a safety gate.

It now reads a Worker secret instead, which means it can only be changed by someone with access to the deployment. And while fixing it I found the related lie: with no email binding configured, a send was still logged as sent and the sequence advanced to the next step, so the system would report a successful campaign that nobody ever received. A send is now logged as sent only when something was actually delivered, and without the binding the step is skipped and stays queued.

Both bugs were found the same way: by looking at what the code does with real input rather than what its tests say. The classifier's tests were all written by the person who wrote the classifier. The send gate was never tested against a request that tried to defeat it.

What is not built

  • Sending is still off. The warm-up ramp, the caps and the suppression checks are all live and tested, but no cold email has been sent, because the domain is not authenticated yet and the mailbox is not warmed. The gate is deliberately closed until it is.
  • No role permissions yet. Everyone signed in can do everything. For a team of four that is fine; it is the first thing to fix if the team grows.
  • No activity feed from other systems. Replies land in the CRM because they are emailed to it, not because anything is integrated. Anything else is still typed in.
  • No reporting beyond the dashboard tiles. The questions that started this are answered, by queries somebody has to run.

What this taught me

  • The smallest system that answers the question beats the smallest system you can build. One Worker and one database is not the point; the point is that a sheet cannot count.
  • A test suite written by the author is not an adversarial review. The classifier had nine passing tests and was wrong on three real sentences. Feed it sentences you did not write.
  • A safety gate must live somewhere the danger cannot reach. A form field is not a safety gate.
  • Never log a success you did not achieve. A send with no delivery is not a send, and a system that reports otherwise is worse than one that reports nothing.
  • Compliance rules belong in the code, not in the process. "Remember to check the list" is not a policy. The check is in every send path, so it cannot be forgotten.

The CRM replaces the sheet, which was the whole job. The interesting part turned out to be everything that happened after the data was in: reading replies, respecting an opt-out, and sending slowly enough that the domain survives it. None of that needed a new framework. It needed somebody to test the parts that decide who gets emailed, with sentences a stranger would write.
