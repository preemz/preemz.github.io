How KerjaBoard Recommends Jobs and Candidates: Two Passes, One Table

Primawan Satrio · November 2026 · ~9 min read

KerjaBoard is the job board my recruiting agency runs on. Its recommendation system answers three questions: which jobs a candidate should see, which candidates a recruiter should call about a job, and who gets an email when a job goes live. An earlier post covers how one candidate and one job become a score. This post covers everything around the score: when it runs, where it is stored, who is told, and how we keep it honest.

The scoring is deterministic. There is no model call per pair, so the same candidate and the same job always produce the same number, and every number carries its reasons. That keeps the system cheap to run across thousands of candidates and makes every failure inspectable. It also means the system is only as good as its rules, which the last section is honest about.

One table, two writers

Every score lives in one table, job_candidate_matches, with one row per job and candidate pair. A row holds the percent, a label, a confidence level, a two-decimal rankKey that breaks ties between equal percents, the rubric version that produced it, a visaGap reason when work authorisation capped the score, and three timestamps recording who has already been told: the candidate emailed, the previous owner nudged, the team announced.

Two code paths write to it, one in each direction.

Figure 1. Both passes write the same table. Readers do not care which pass produced a row, with one exception: only the candidate pass writes visaGap. Only the job pass is allowed to send mail or post to the team.
  • The job pass. When a job goes live, whether a recruiter publishes it or an admin approves an employer’s post, the job is scored against every eligible candidate, which leaves out anyone who objected to sourcing and, for EU orders, anyone who declared a region outside the EU. This is the only pass that can send anything.
  • The candidate pass. When a candidate saves a CV, applies to a job or answers the work-status questions, that candidate is scored against every live job. It writes rows and nothing else. It never emails and never announces.

Why both? The job pass alone leaves a gap: a candidate who registers on Tuesday has no scores against jobs published on Monday. The candidate pass alone cannot tell a recruiter who to call the moment a job goes live. Each covers the other’s blind spot, and because both write the same rows under the same rubric, readers rarely need to know which one ran. The one difference is that the visa reason is written only by the candidate pass.

Delivery belongs to one writer

Two writers risk a double send. A candidate pass that re-scores a pair must never clear the flag saying that pair was already emailed. Both upserts list the columns they refresh, and the three notification timestamps are not among them, so one CV upload cannot re-mail old matches. The delete that prunes a candidate’s stale rows also skips any row that has been emailed.

A new job emails a candidate only if the match clears every gate below.

The volume cap had a bug worth telling. It first counted emails sent. Candidates who had already been notified were skipped without using a slot, so every re-publish or admin “re-run the engine” press could mail up to 25 more people. Four presses, a hundred emails. The cap now counts everyone who qualifies, whether or not they are mailed this time, so repeating the run cannot exceed it.

The same pass also tells the team. A strong match whose previous owner’s three-month ownership window has expired produces a nudge to that owner, in one channel for internal staff and another for freelancers. A strong match with no owner is announced so someone can claim the candidate. Staff also see a count of strong matches on the job page. Candidates never see that count.

Region and visa: rank, badge, never hide

What a candidate sees is a read of stored rows, never a computation inside the page request. Three surfaces read them: a short list on the homepage, an Apply next block after an application, and a full For you page. They use a lower floor than staff do, 40% against 60%, because after the skill caps a candidate can honestly have nothing above 60, and an empty block makes the feature look broken. Possible fits rank below strong ones. On the site, candidates see a fit label, not the percentage.

Work authorisation shows how two correct layers can build a trap. The scorer caps a match at 30% when a candidate needs sponsorship the order does not offer, and at 20% when they cannot work in the region. The display floor is 40%. So the capped jobs were dropped before the page rendered them, and the visa badge written to explain them could never appear. Each layer was right on its own.

The fix records the reason when the score is computed. The row stores visaGap, the list waives the floor for rows that carry one, and it orders them after every uncapped match. The candidate sees the job, ranked low, with a badge saying why. The product rule is now: show every job, rank the ones the candidate cannot legally take lower, and say why.

Region follows the same rule. The list keeps roles in the candidate’s own region, roles marked global, and roles whose location says remote. The rest move to a separate section on the For you page, with a count on the homepage. An early version of the “show the hidden roles” link only dropped the filter and kept the three-card limit. The hidden rows were visa-capped and sorted last, so the same three cards came back and it looked as if recommendations ignored region. A link that promises N rows has to open a list that contains them.

One SQL detail cost a debugging session. An unlabelled job has a NULL region, and NOT (NULL) is NULL, so such a job landed in neither the in-region list nor the outside list, while a count written with CASE WHEN still counted it. The page said one, the database said forty-one. Every region test in the recommendation queries now goes through IFNULL(regulatoryRegion, 'ID').

Keeping scores honest after the rules change

A score stored under old rules is a promise nobody can keep. The rubric has a version number and both directions stamp it. Candidate pages only show rows carrying the current version, and when none qualify they fall back to a keyword search instead of quoting a number we no longer stand behind. (The earlier post tells how a missing job-side half of this once left a flat 100% on an order after the rubric had changed.)

Two sweeps in the 15-minute cron drain the backlog after a version bump.

  • Candidate warm-up. It walks 20 candidates per tick whose stamp is missing or older, and parses at most 8 CVs per tick, because a parse costs a storage read plus a PDF decode. A candidate without cached CV text waits for the next tick instead of being stamped current on thin data.
  • Job sweep. It takes one live order per tick, newest first, and rewrites up to 200 of its stale rows, strongest score first, because the top of a list is what recruiters read.

The candidate-side stamp sits on the user, not on the match rows. A row-level stamp would keep anyone whose CV legitimately matches nothing in the queue for ever, parsing their resume every tick without ever writing a row to satisfy it.

The sweeps must not become the problem themselves. D1 runs one query at a time, and after a bump the stale set is large. A count over it on every tick blocked logins and tracker moves, which failed with D1 internal errors at quarter past. A per-order EXISTS probe fixed it: the cost of a tick no longer grows with the size of the backlog. A related planner trap: rubric IS NULL OR rubric < V made D1 read the whole table, about 256,000 rows, to find a few thousand. Splitting it into two UNION ALL halves brought the count query down to about 2.5% of that many rows read.

Fitting inside a Worker

The first version of the job pass scored every candidate inside the publish request, parsing each resume from storage. It died with Cloudflare’s “exceeded resource limits” error (1102) once the candidate base grew into the thousands. Four changes made it fit.

  • Parse once. Each candidate carries a cached copy of their CV text and terms, filled when the CV is uploaded. Scoring reads the cache instead of fetching and decoding a PDF.
  • Write in batches. D1 allows about 100 bound parameters per statement, so the chunk size is the cap divided by parameters per row, rounded down: 11 rows at 9 parameters. At 10 parameters it is 9, one under what the arithmetic allows, because 10 rows would land exactly on the cap. A chunk of 18 rows, sized before two columns were added, once became 126 variables and failed on every publish. The arithmetic now sits in a comment beside the constant.
  • Skip pairs with no signal. A zero score writes no row, and on the candidate side it prunes the row it replaces.
  • Run it after the response. Publishing hands the job to waitUntil, so a slow or broken recommender cannot fail the publish.

How it fails silently

Because publishing must never fail on account of the recommender, its errors are caught and turned into a metric, and the publisher still sees “the job is live”. That is the right call for the person publishing and a risky one for the system: nothing on the publish screen shows that scoring died, and a broken scorer produces the same empty result as a candidate base with no matches.

In September a change to the job pass read a block-scoped constant after its try block. On the first scored candidate it threw a ReferenceError. Publishing still said the job went live. The pass wrote no rows, sent no emails and announced nothing, and the interface said nothing about it. The only trace was an error line in the monitoring channel, easy to read as noise. No test in the suite calls the pass, so nothing failed before the deploy.

Two habits came out of it. After any change to the pass, I run the real module in Node with a stubbed data layer and assert that it finishes and writes one row per scored candidate. And background work needs a positive signal, not only an error alarm: the pass logs candidates, scored and matching counts on every run, so a pass that did nothing shows up as a missing line.

The sweeps have the same disease. A sweep that throws every tick, and one that runs and does nothing, look just like one with nothing to do. So a watchdog compares the two: if an open order still has stale rows the sweep could rewrite and the tick rewrote none, it posts to the monitoring channel.

The loudest alert can be as bad as none. The first metric wrapper posted one line per scored candidate to the team’s monitoring channel, in bursts of twenty from the warm-up. Success lines now go to the logs, and the channel only hears about error-class events.

The last silent failure is the input. Some PDFs use fonts that decode one-to-one to the wrong letters, so “Government” arrives as punctuation soup that is still plain ASCII. A sales director’s CV parsed into exactly two terms, C# and R, and scored 93% against a foodtech R&D role. A readability gate now rejects text that is under about half letters, and the scorer falls back to the profile alone instead of inventing matches.

What is still weak

  • The thresholds are judgment, not calibration. The cut-offs (72 to email, 60 to highlight, 40 to show) came from reading real lists. Recruiters can mark a fit score as right or wrong, and that table is empty, so there is no disagreement rate to tune against. Application outcomes are a noisy substitute, since a rejection can be about salary or a filled seat. So far there is no human-labelled set of pairs to measure against.
  • Team notifications are not capped like email. The ceiling is 25 emails per publish, but owner nudges and unowned-candidate announcements run for every strong match. A thin order can make that channel loud.
  • The passes have no automated test. The scorer has invariant tests and the For you page runs real handlers against the real schema. Neither pass, the delivery rules nor the sweeps has a guard in CI. The stub check above is something I run by hand.
  • It matches words, not meaning. Skills and years are read from text, so a candidate who describes the same work in different words scores lower. An AI-written fit note exists, but only for submitted applications and as a separate read for recruiters. It does not feed recommendations.

The score was the easy part. Most of the work went into who gets told, whether a stored number still means what it says, and making failure audible.
