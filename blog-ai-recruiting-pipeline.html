An End-to-End AI Recruiting Pipeline in Production

Primawan Satrio · August 2026 · ~10 min read

Most AI demos die in the demo. The interesting question is not can a model do this once, but can it run inside a live business every day, without a human babysitting every step. I run a headhunting agency across the Indonesia–Japan corridor, and instead of bolting AI onto the side, I rebuilt our recruiting pipeline around it: parsing resumes, scoring candidate fit, reformatting CVs into client templates, and engaging candidates automatically.

This post explains how the pipeline works, why each stage is designed the way it is, and what I learned deploying LLMs where mistakes cost real placements. It runs on Cloudflare Workers with D1 for data and R2 for document storage — no origin server anywhere.

The pipeline at a glance

A candidate's journey through our system touches four AI-assisted stages before a recruiter ever picks up the phone:

Figure 1 — The production pipeline. Stages 2 and 4 are fully automated; stage 3 is deliberately human.

Stage 1: Reading any resume reliably

Resumes arrive as PDF or DOCX in any layout, half of them from Indonesian candidates mixing Bahasa and English. Before an LLM sees anything, deterministic code extracts plain text and mines structure with rules tuned to real-world messiness:

  • Tenor parsing. Employment date ranges like Jan 2020 – Present, 2021–2023, or s/d sekarang are extracted to compute tenure months per role — which later feeds both stability scoring and seniority inference.
  • Skill canonicalization. An alias map collapses sklearn, scikit-learn, and Scikit Learn to one canonical skill so counts don't fragment.
  • Date normalization. Indonesian CVs write dates day-first (14/08/1995), European style. The normalizer disambiguates ambiguous numeric dates rather than guessing wrong.
Design rule: use the LLM where language understanding is genuinely needed (summaries, unstructured fields, template mapping). Use deterministic parsing where a regex is more reliable, free, and auditable. Hybrid beats pure-LLM on both cost and consistency.

Stage 2: Explainable fit scoring

Given a job order and a parsed resume, the scoring engine estimates how well this candidate fits — but the design constraint that shaped everything was explainability: every point in the score must come with a reason a recruiter can read, agree or disagree with, and act on.

Figure 2 — Weighted components with dynamic re-normalization. Weights only count when the job order expresses that dimension.

Fairness guardrails are a feature, not a checkbox

We collect date of birth for client paperwork. The scoring module never reads it — and there is a test asserting two identical candidates with different birth dates receive identical scores. Name, gender, nationality, photo, and university prestige are likewise excluded by construction, not by prompt politeness. If you're deploying models on people, this class of guarantee belongs in your test suite, next to your business logic.

Stage 3: The human in the loop, on purpose

The recruiter sees the score with its reasons. This matters because a naked number invites either blind trust or blind dismissal; reasons invite calibration. Over time recruiters learn where the model over-weights and where their own judgment should override — which is exactly the collaboration pattern you want between humans and automated screening.

Ownership stays manual by design: no application is ever auto-assigned or auto-rejected. Automation triages; humans decide. In recruiting, a false negative (rejecting someone who would have placed) costs more than a few minutes of recruiter time.

Stage 4: LLM-powered CV reformatting

When a candidate advances, each client expects their own submission format — a specific DOCX template with particular sections and phrasing. Historically recruiters retyped resumes into these formats by hand: hours per placement. Now:

  1. Each client format is declared as a schema: field keys, labels, groupings, hints, repeating blocks (employment history).
  2. The schema generates three artifacts from one source of truth: the LLM prompt, the recruiter review form, and the template fill.
  3. The LLM (OpenAI or Anthropic, provider-swappable via config) receives the raw CV text plus the target schema and returns structured JSON.
  4. A tolerant JSON parser handles the reality of LLM output — markdown fences, trailing commas, chatty preambles.
  5. The recruiter reviews extracted fields in the browser and corrects anything wrong; the corrected data fills the client's DOCX.

The schema-driven approach is the key trick: adding a new client format means writing one declarative object, not new prompt engineering. The prompt can't drift out of sync with the form or the template, because they're all projections of the same definition.

What production taught me

  • Deterministic-first architecture pays twice. Rules handle the structured 80% of a resume cheaply and consistently; the LLM handles the messy 20%. Costs stay predictable and failures stay debuggable.
  • Explainability is a product requirement, not an ethics poster. Recruiters adopted the scoring engine because they could interrogate it. A black-box score would have been ignored — correctly.
  • Provider abstraction is cheap insurance. Supporting OpenAI-compatible and Anthropic APIs behind one interface took an afternoon and means model swaps are config changes, not migrations.
  • Human-in-the-loop is where trust compounds. Every recruiter correction is implicit labeled data. The pipeline gets better not by retraining, but because the design routes uncertainty to the person best placed to resolve it.
  • Fairness constraints belong in tests. If a protected attribute must not influence a decision, prove it with an assertion, not a policy memo.

Papers worth reading alongside this

If you want to go deeper on the research behind these design choices, start here:

  • Ribeiro et al., ""Why Should I Trust You?": Explaining the Predictions of Any Classifier" (KDD 2016) — arXiv:1602.04938. The LIME paper; foundational for why local, reason-level explanations drive user trust — the same principle behind showing recruiters why a candidate scored as they did.
  • Lundberg & Lee, "A Unified Approach to Interpreting Model Predictions" (NeurIPS 2017) — arXiv:1705.07874. SHAP: attribute decisions to input features fairly. Useful mental model even when your "model" is a weighted rule engine.
  • Buolamwini & Gebru, "Gender Shades" (FAT* 2018) — PMLR v81. The canonical demonstration that systems processing people carry bias unless audited. Motivates testing fairness properties explicitly.
  • Raji et al., "Closing the AI Accountability Gap: Defining an End-to-End Framework for Internal Algorithmic Auditing" (2020) — arXiv:2001.00973. How to build audit scaffolding (like our birth-date-blindness test) into the development lifecycle.
  • Wang et al., "Human-AI Collaboration in Data Science" and related work on human-in-the-loop ML — a good entry point is Amershi et al., "Guidelines for Human-AI Interaction" (CHI 2019) — Microsoft Research. Eighteen concrete guidelines; our "show reasons, keep the decision human" pattern maps directly onto several of them.
  • Kocijan et al. / resume-parsing literature: for the information-extraction side, see the SemEval shared tasks on CV parsing and Decorte et al., "Skill Detection in Job Profiles" (2021) — arXiv:2111.13319 — on extracting and normalizing skills from noisy professional text.
  • Vaswani et al., "Attention Is All You Need" (2017) — arXiv:1706.03762. Included for completeness: the transformer backbone under every LLM stage of this pipeline.

Wrapping up

None of the individual pieces here is exotic: regexes, weighted scoring, an LLM call behind a schema, a WhatsApp bot. The engineering value — and the forward-deployed mindset — lives in the seams: knowing which problems need a model and which need a regex, making automated judgments inspectable, keeping humans on the decisions that deserve them, and proving fairness claims with tests. That's the difference between an AI demo and an AI pipeline a real business runs on.
