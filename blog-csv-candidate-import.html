Importing thousands of candidates without breaking a single record

Primawan Satrio · August 2026 · ~8 min read

When we moved our recruiting operation onto our own platform, the hardest part was not the job board or the application flow. It was the database: years of candidate records living in a Lark base, with column names in a mix of English and Bahasa Indonesia, phone numbers formatted six different ways, and the same people entered more than once by different recruiters. A naive import would have created phantom duplicates that our team would chase for months.

This post covers the CSV importer we built to solve that: a forgiving parser, smart column mapping, and a dry-run preview that shows exactly what will happen to every row before anything is written. The feature now lives at /admin/import and recruiters use it whenever a client or partner sends over a spreadsheet of candidates.

Parsing: assume the file is worse than it is

Spreadsheet exports are hostile. Real files we received contained a UTF-8 byte-order mark, CRLF line endings from Windows Excel, quoted fields with embedded commas and newlines, doubled quotes inside quoted fields, and trailing blank lines. Rather than pull in a dependency on a Workers-sized budget, we wrote a ~60-line RFC 4180 parser that handles all of it:

  • Byte-order mark stripping so the first header is not silently corrupted into ï»¿email
  • Proper quote state machine with escaped-quote handling ("" inside a quoted field)
  • Blank-row filtering and whitespace trimming on every cell
Design rule: every quirk in this parser exists because a real export contained it. When your parser meets a new quirk in production, fix the parser, not the file.

Column mapping: meet the spreadsheet where it is

The next problem is that exports never use your field names. Our Lark base called the email column everything from Email Address to e-mail to surel (Indonesian for email). Instead of forcing a rigid template, the importer guesses the mapping using an alias table, with Indonesian aliases as first-class citizens:

Our fieldHeaders we accept
emailemail, emailaddress, mail, workemail, surel
namefullname, name, candidatename, namalengkap, nama
phonephone, mobile, whatsapp, wa, nohp, telepon
dateOfBirthdob, birthdate, birthday, tanggallahir, ttl
locationcity, domicile, address, domisili, kota
Header matching is done on a normalized form: lowercased, everything but letters and digits stripped, so "E-Mail Address" matches "emailaddress".

The guesser has two rules that matter. First, it never maps the same column twice: once a header is claimed by a field, it is removed from the pool, so two similar columns cannot both feed one field. Second, every guess is shown to the admin on a review screen where any choice can be overridden before committing. The machine proposes; a human disposes.

The dry-run: no surprises allowed

The part I am most insistent on is that nothing is written to the database until the admin has seen, row by row, what will happen. Upload lands on a review page showing every row classified into one of five actions:

  • create — valid, unknown email, will be imported
  • invalid — missing or malformed email, or missing name; excluded with the reason shown
  • duplicateInFile — same email appeared on an earlier line of this same file
  • alreadyRegistered — this person already has an account on the platform
  • ownedByRecruiter — the person sits in a recruiter's talent pool with an active ownership window; the import names the recruiter and the expiry date

Email is the identity key for all of it. Everything deduplicates on the normalized (lowercased) email address, because in our business the email is the one field that reliably identifies a person across systems, while names collide and phone numbers change format.

Performance: two passes, not one per row

The deduplication check needs to query the database per row, and on Cloudflare Workers a naive loop of one query per row is exactly the pattern that eats your subrequest budget. The preview instead runs in two passes:

  1. Synchronous first pass over the file itself: validate emails, require names, detect in-file duplicates with a set. No database involved, and ordering stays strict so "same email appears earlier in this file" is always accurate.
  2. Parallel second pass over the surviving rows: batched lookups against registered users and active recruiter ownerships, run concurrently rather than sequentially.

Every import is also recorded with its filename, headers, mapping, and who uploaded it, so a bad import can be audited after the fact rather than wondered about.

What this taught us

  • Dedupe on identity, not on rows. The unit of truth is the person (by email), not the spreadsheet line. Getting this wrong is how companies end up calling the same candidate twice from two "different" records.
  • Show the future before you create it. A dry-run preview that classifies every row converts an import from an act of faith into a reviewable decision. The admin who sees "owned by Mikke until 2026-11-30" trusts the system; the one who sees a spinner does not.
  • Bilingual data needs bilingual tooling. Half our header aliases are Indonesian because our data is Indonesian. Tooling that only understands English column names would have made every import a manual mapping exercise.
  • A ~60-line parser beats a dependency when you know exactly what you must survive. RFC 4180 is small, and owning the code means the next weird export is a one-line fix away.

The importer looks mundane next to LLM pipelines and scoring engines, but it is the feature that made the rest trustworthy: the match engine can only be as good as the candidate data underneath it, and this is how that data got in cleanly.
